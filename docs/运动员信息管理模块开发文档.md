## 1. 模块概述

### 1.1 模块定位

运动员信息管理模块是"乒乓球运动员综合训练监控管理系统"的**基础数据模块**，负责运动员档案的全生命周期管理。所有其他业务模块（训练计划、专项技术、体能测试、伤病记录、比赛成绩）均以运动员为关联主体，因此本模块的数据完整性和查询效率直接影响整个系统的运行质量。

### 1.2 功能清单

| 序号 | 功能 | 说明 |
|------|------|------|
| 1 | 运动员列表查询 | 支持 8 个维度的多条件动态组合筛选，AND/OR 逻辑切换 |
| 2 | 运动员档案详情 | 聚合展示基本信息、训练统计、技术评估、体能测试、伤病记录、比赛成绩 |
| 3 | 新增运动员 | 表单验证 + 学号唯一性检查 + MySQL INSERT |
| 4 | 编辑运动员 | 数据回填 + 字段校验 + MySQL UPDATE |
| 5 | 删除运动员 | 二次确认 + 级联删除（数据库外键 CASCADE） |
| 6 | 存储过程调用 | 按运动等级筛选运动员（`CALL sp_filter_athletes_by_level`） |

## 2. 数据库表设计

### 2.1 athlete 表结构

```sql
CREATE TABLE athlete (
    id              INT             AUTO_INCREMENT  PRIMARY KEY,
    student_no      VARCHAR(20)     NOT NULL UNIQUE,
    name            VARCHAR(50)     NOT NULL,
    gender          ENUM('男','女') NOT NULL,
    birth_date      DATE,
    team            VARCHAR(100),
    skill_level     ENUM('二级运动员','一级运动员','国家级','健将级','青年队') NOT NULL,
    play_style      VARCHAR(100),
    grip            VARCHAR(50),
    contact_phone   VARCHAR(20),
    injury_status   ENUM('健康','观察中','康复中','伤病中')
                        NOT NULL DEFAULT '健康',
    create_time     TIMESTAMP       DEFAULT CURRENT_TIMESTAMP,
    update_time     TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8;
```

### 2.2 字段设计说明

| 字段 | 类型 | 约束 | 设计意图 |
|------|------|------|----------|
| `id` | INT AUTO_INCREMENT | PRIMARY KEY | 系统内部唯一标识，自增主键 |
| `student_no` | VARCHAR(20) | NOT NULL, UNIQUE | 学校/队伍中的唯一编号，支持模糊查询 |
| `name` | VARCHAR(50) | NOT NULL | 运动员姓名，支持 LIKE 模糊匹配 |
| `gender` | ENUM('男','女') | NOT NULL | 性别，限定取值防止脏数据 |
| `birth_date` | DATE | 可空 | 出生日期，用于自动计算年龄 |
| `team` | VARCHAR(100) | 可空 | 所属队伍（校队/省队等） |
| `skill_level` | ENUM(5个值) | NOT NULL | 运动等级，按国家体育总局标准 |
| `play_style` | VARCHAR(100) | 可空 | 技术打法描述（如"右手横板快攻结合弧圈"） |
| `grip` | VARCHAR(50) | 可空 | 握拍方式（如"右手横板"） |
| `contact_phone` | VARCHAR(20) | 可空 | 联系电话 |
| `injury_status` | ENUM(4个值) | NOT NULL, DEFAULT '健康' | **触发器预留字段**，由 injury_record 触发器的自动维护 |
| `create_time` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | 记录创建时间 |
| `update_time` | TIMESTAMP | 可空 | 记录最后修改时间，UPDATE 时手动设置为 NOW() |

### 2.3 索引设计

```sql
-- 姓名索引：加速按姓名模糊查询
CREATE INDEX idx_athlete_name ON athlete(name);

-- 复合索引：加速按运动等级 + 伤病状态的组合筛选
CREATE INDEX idx_athlete_level_status ON athlete(skill_level, injury_status);
```

**索引选择原理**：
- `idx_athlete_name`: 运动员列表页默认按姓名搜索，LIKE 查询走索引比全表扫描快 10~100 倍
- `idx_athlete_level_status`: 统计分析大屏经常按等级+状态分组统计，复合索引避免回表

### 2.4 外键关系

athlete 表是系统中的**父表**，被以下子表引用：

| 子表 | 外键列 | 删除策略 | 说明 |
|------|--------|----------|------|
| training_plan | athlete_id | CASCADE | 删除运动员 → 训练计划自动删除 |
| technical_record | athlete_id | CASCADE | 删除运动员 → 技术记录自动删除 |
| fitness_report | athlete_id | CASCADE | 删除运动员 → 体能报告自动删除 |
| injury_record | athlete_id | CASCADE | 删除运动员 → 伤病记录自动删除 |
| match_record | athlete_id | CASCADE | 删除运动员 → 比赛记录自动删除 |

> **设计决策**: 全部使用 CASCADE，因为运动员删除后，其关联的业务数据失去意义。但 training_plan → coach 使用 RESTRICT，防止教练被误删导致训练计划出现孤儿数据。

## 5. 多条件动态组合查询设计（核心）

### 5.1 设计目标

运动员档案列表页是系统最高频使用的查询入口。设计目标是：

1. **多维度覆盖**：支持学号、姓名、性别、运动等级、打法、握拍方式、伤病状态、年龄范围共 8 个筛选维度
2. **模糊匹配**：文本类字段（学号、姓名、打法、握拍）使用 LIKE 模糊匹配，降低用户输入门槛
3. **逻辑切换**：支持 AND（同时满足）和 OR（任一满足）两种条件组合逻辑
4. **参数化查询**：使用 `%s` 占位符和参数列表，防止 SQL 注入
5. **URL 可分享**：所有查询参数通过 URL query string 传递，支持浏览器书签和分享

### 5.2 整体架构——filter_list 构建模型

多条件组合查询的本质是将 **"用户输入 → SQL WHERE 子句"** 的映射过程结构化。系统使用一个统一的 `filter_list` 数据结构作为中间表示：

```
用户表单输入                        filter_list                      SQL WHERE 子句
┌────────────┐                 ┌──────────────────┐            ┌─────────────────────┐
│ student_no │──── LIKE ──────▶│ ("s_no LIKE %s",  │            │ WHERE s_no LIKE %s  │
│ name       │──── LIKE ──────▶│  "name LIKE %s",  │──build────▶│   AND name LIKE %s  │
│ gender     │──── = ─────────▶│  "gender = %s",   │  _where   │   AND gender = %s   │
│ skill_level│──── = ─────────▶│  "level = %s",    │  _clause  │   AND level = %s    │
│ play_style │──── LIKE ──────▶│  "style LIKE %s", │           │   AND style LIKE %s │
│ grip       │──── LIKE ──────▶│  "grip LIKE %s",  │           │   AND grip LIKE %s  │
│ injury_st  │──── = ─────────▶│  "status = %s",   │           │   AND status = %s   │
│ age_min    │──── >= ────────▶│  "age >= %s",     │           │   AND age >= %s     │
│ age_max    │──── <= ────────▶│  "age <= %s",     │           │   AND age <= %s     │
└────────────┘                 └──────────────────┘            └─────────────────────┘
    用户界面                      统一中间表示                     最终 SQL 片段
  (request.args)               (filter_list)                    (占位符 + 参数列表)
```

这种设计有 3 个核心优势：
- **关注点分离**：前端表单 → filter_list 是数据提取层，filter_list → SQL 是拼接层，互不干扰
- **可测试性强**：给定 filter_list 就能直接验证生成的 SQL 是否正确
- **易于扩展**：新增筛选维度只需在 filter_list 中追加一个元组

### 5.3 核心函数

```python
# db.py

def build_where_clause(filters, logic="AND"):
    """动态构建 SQL WHERE 子句。

    参数:
        filters: 筛选条件列表，每个元素为 (condition_sql, param_value) 元组
        logic: 条件连接逻辑，"AND" 或 "OR"

    返回:
        (where_clause_str, params_list)
    """
    conditions = []
    params = []

    for condition_sql, param_value in filters:
        # 跳过空值条件（None、空字符串）——动态拼接的核心
        if param_value is None or (isinstance(param_value, str) and param_value.strip() == ""):
            continue
        conditions.append(condition_sql)
        params.append(param_value)

    if not conditions:
        return "", []  # 无条件时返回全部数据

    separator = f" {logic} "
    where_clause = " WHERE " + separator.join(conditions)
    return where_clause, params
```

### 5.4 实际查询示例

#### 示例 1：单一条件查询

用户输入：姓名 = "王"

```python
filters = [
    ("athlete.name LIKE %s", "%王%"),
]
# build_where_clause 输出:
# (" WHERE athlete.name LIKE %s", ["%王%"])
# 最终 SQL:
# SELECT * FROM athlete WHERE athlete.name LIKE '%王%'
```

#### 示例 2：AND 组合查询（3 个条件）

用户输入：性别 = "男", 等级 = "一级运动员", 年龄范围 18-22

```python
filters = [
    ("athlete.gender = %s", "男"),
    ("athlete.skill_level = %s", "一级运动员"),
    ("YEAR(CURDATE()) - YEAR(athlete.birth_date) >= %s", 18),
    ("YEAR(CURDATE()) - YEAR(athlete.birth_date) <= %s", 22),
]
# 非空条件: gender, skill_level, age_min, age_max (4条)
# build_where_clause 输出:
# (" WHERE athlete.gender = %s AND athlete.skill_level = %s
#    AND YEAR(CURDATE()) - YEAR(athlete.birth_date) >= %s
#    AND YEAR(CURDATE()) - YEAR(athlete.birth_date) <= %s",
#  ["男", "一级运动员", 18, 22])
```

#### 示例 3：OR 组合查询（3 个条件）

用户输入：姓名 = "王", 打法 = "弧圈", 伤病状态 = "伤病中"

```python
filters = [
    ("athlete.name LIKE %s", "%王%"),
    ("athlete.play_style LIKE %s", "%弧圈%"),
    ("athlete.injury_status = %s", "伤病中"),
]
logic = "OR"
# build_where_clause 输出:
# (" WHERE athlete.name LIKE %s OR athlete.play_style LIKE %s
#    OR athlete.injury_status = %s",
#  ["%王%", "%弧圈%", "伤病中"])
```

### 5.5 AND vs OR 逻辑对比

| 特性 | AND（同时满足） | OR（任一满足） |
|------|-----------------|-----------------|
| 默认 | ✅ 是 | - |
| 适用场景 | 精确筛选，逐步缩小范围 | 宽泛搜索，扩大命中范围 |
| 结果集大小 | 较小（交集） | 较大（并集） |
| 典型用例 | "一级运动员 + 男 + 健康" | "包含'王' 或 包含'弧圈' 或 伤病中" |
| SQL 连接词 | `AND` | `OR` |

### 5.6 年龄范围查询的特殊处理

年龄不是 athlete 表的直接字段，而是从 `birth_date` 计算得出：

```sql
-- 年龄计算
YEAR(CURDATE()) - YEAR(athlete.birth_date)

-- 年龄范围筛选（>= 18 且 <= 22）
YEAR(CURDATE()) - YEAR(athlete.birth_date) >= 18
AND YEAR(CURDATE()) - YEAR(athlete.birth_date) <= 22
```

**为什么不存储年龄字段**：
- 年龄是派生数据，会随时间变化
- 存储 birth_date 可以从源头计算，保证准确性
- 避免每年需要批量更新年龄字段的维护成本

### 5.7 LIKE 模糊匹配的安全处理

```python
def build_like_pattern(keyword):
    """构建 LIKE 模糊匹配模式，转义特殊字符。"""
    if not keyword:
        return None
    # 转义 LIKE 通配符 \% 和 \_
    escaped = keyword.replace("%", r"\%").replace("_", r"\_")
    return f"%{escaped}%"
```

**为什么需要转义**：
- SQL LIKE 中 `%` 匹配任意字符串，`_` 匹配单字符
- 如果用户输入包含 `%` 或 `_`（如搜索"100%专注"），不转义会导致意外匹配
- 转义后 `%` 和 `_` 被视为普通字符，而非通配符

## 6. 动态 WHERE 条件拼接逻辑

### 6.1 设计原理

动态 WHERE 条件拼接的核心思想是 **"空值跳过，非空拼接"**。这种方法避免了以下常见问题：

1. **硬编码 WHERE 1=1**：传统做法 `WHERE 1=1 AND name LIKE ...` 虽可行但不优雅
2. **大量 if-else 分支**：8 个条件 × AND/OR 两种模式 = 可爆炸出大量分支
3. **SQL 注入风险**：字符串拼接 SQL 极易被注入

本系统的解决方案：**遍历 filter_list → 过滤空值 → 统一拼接**，将复杂度从 O(2^n) 降为 O(n)。

### 6.2 实现代码（players.py 中调用）

```python
@players_bp.route("/", endpoint="list")
def players_list():
    # 1. 获取全部查询参数
    student_no = request.args.get("student_no", "").strip()
    name = request.args.get("name", "").strip()
    gender = request.args.get("gender", "").strip()
    # ... 其余字段类似

    # 2. 构建 filter_list
    filter_list = [
        ("athlete.student_no LIKE %s", build_like_pattern(student_no)),
        ("athlete.name LIKE %s", build_like_pattern(name)),
        ("athlete.gender = %s", gender if gender else None),
        ("athlete.skill_level = %s", skill_level if skill_level else None),
        ("athlete.play_style LIKE %s", build_like_pattern(play_style)),
        ("athlete.grip LIKE %s", build_like_pattern(grip)),
        ("athlete.injury_status = %s", injury_status if injury_status else None),
        ("YEAR(CURDATE()) - YEAR(athlete.birth_date) >= %s",
         int(age_min) if age_min.isdigit() else None),
        ("YEAR(CURDATE()) - YEAR(athlete.birth_date) <= %s",
         int(age_max) if age_max.isdigit() else None),
    ]

    # 3. 调用核心函数
    where_clause, params = build_where_clause(filter_list, logic=logic)

    # 4. 拼接并执行 SQL
    sql = f"SELECT * FROM athlete{where_clause} ORDER BY id DESC"
    players = execute_query(sql, tuple(params))
```

### 6.3 参数化查询防注入

```python
# ❌ 危险：字符串拼接
```

## 8. injury_status 伤病状态字段的触发器适配方案

### 8.1 设计背景

`athlete.injury_status` 是一个**冗余派生字段**——它的值完全取决于 `injury_record` 表中该运动员的所有未恢复记录。但出于查询性能考虑（运动员列表是最频繁访问的页面），将此字段冗余存储在 athlete 表中，避免每次列表查询都需要 JOIN + GROUP BY injury_record。

这种"冗余存储"模式面临的核心挑战是**数据一致性**：当 injury_record 发生增删改时，athlete.injury_status 必须同步更新。

### 8.2 为什么不直接在应用层更新

| 方案 | 优点 | 缺点 |
|------|------|------|
| 应用层更新（Python代码） | 逻辑可见、易调试 | 多处代码需重复逻辑、容易遗漏（如 DELETE 时忘记更新） |
| 数据库触发器 | 自动执行、永不遗漏、一处生效全局 | 调试不便、出错时不易排查 |

对于数据一致性要求高的场景，触发器是更可靠的选择。

### 8.3 触发器架构

```
injury_record 表
      │
      ├── AFTER INSERT → trg_injury_after_insert
      │                   └── CALL sp_refresh_athlete_injury_status(NEW.athlete_id)
      │
      ├── AFTER UPDATE → trg_injury_after_update
      │                   └── CALL sp_refresh_athlete_injury_status(NEW.athlete_id)
      │                       CALL sp_refresh_athlete_injury_status(OLD.athlete_id)  -- 若运动员变更
      │
      └── AFTER DELETE → trg_injury_after_delete
                          └── CALL sp_refresh_athlete_injury_status(OLD.athlete_id)
```

### 8.4 存储过程逻辑

```sql
CREATE PROCEDURE sp_refresh_athlete_injury_status(IN p_athlete_id INT)
BEGIN
    UPDATE athlete
    SET injury_status = (
        SELECT
            CASE
                -- 优先级 1: 有「严重」+「治疗中」→ 伤病中
                WHEN SUM(CASE WHEN recovery_status = '治疗中' AND severity = '严重'
                         THEN 1 ELSE 0 END) > 0
                    THEN '伤病中'
                -- 优先级 2: 有「治疗中」→ 观察中
                WHEN SUM(CASE WHEN recovery_status = '治疗中'
                         THEN 1 ELSE 0 END) > 0
                    THEN '观察中'
                -- 优先级 3: 有「康复中」(无治疗中) → 康复中
                WHEN SUM(CASE WHEN recovery_status = '康复中'
                         THEN 1 ELSE 0 END) > 0
                    THEN '康复中'
                -- 优先级 4: 无未恢复伤病 → 健康
                ELSE '健康'
            END
        FROM injury_record
        WHERE athlete_id = p_athlete_id
          AND recovery_status IN ('治疗中','康复中')
    )
    WHERE id = p_athlete_id;
END
```

### 8.5 状态判定优先级

```
┌──────────────────────────────────────────────────┐
│  从 injury_record 读取该运动员未恢复的伤病         │
│  (recovery_status IN ('治疗中','康复中'))          │
└────────────────────┬─────────────────────────────┘
                     │
        ┌────────────▼────────────┐
        │ 有"严重"+"治疗中"伤病？   │── 是 ──▶ 伤病中
        └────────────┬────────────┘
                     │ 否
        ┌────────────▼────────────┐
        │ 有"治疗中"伤病？         │── 是 ──▶ 观察中
        └────────────┬────────────┘
                     │ 否
        ┌────────────▼────────────┐
        │ 有"康复中"伤病？         │── 是 ──▶ 康复中
        └────────────┬────────────┘
                     │ 否
                     ▼
                   健康
```

### 8.6 应用层适配方案

虽然在数据库层通过触发器自动维护 injury_status，但应用层也做了以下适配：

1. **编辑页暴露字段**：管理员在编辑运动员时可以看到并手动修改 injury_status 字段（用于特殊情况修正），但表单中有明确提示"由触发器自动维护，一般无需手动修改"

2. **详情页展示机制说明**：管理员在运动员详情页可以看到触发器和存储过程的调用说明，便于理解数据来源

3. **新建默认为"健康"**：新增运动员时自动设置 `injury_status = '健康'`，符合业务逻辑

4. **写入操作不主动变更**：运动员模块的 INSERT/UPDATE 语句不主动设置 injury_status（除非管理员在编辑页手动更改），避免与触发器产生冲突

### 8.7 一致性验证 SQL

```sql
-- 检查运动员伤病状态是否与伤病记录一致
SELECT
    a.id,
    a.name,
    a.injury_status AS 当前状态,
    COUNT(ir.id) AS 未恢复伤病数,
    GROUP_CONCAT(CONCAT(ir.injury_location, '(', ir.severity, '/', ir.recovery_status, ')')) AS 详情
FROM athlete a
LEFT JOIN injury_record ir
    ON ir.athlete_id = a.id AND ir.recovery_status IN ('治疗中','康复中')
GROUP BY a.id, a.name, a.injury_status
HAVING a.injury_status != '健康' AND COUNT(ir.id) = 0
    OR a.injury_status = '健康' AND COUNT(ir.id) > 0;
-- 如果返回空结果集，说明触发器工作正常，数据一致
```


### 12.2 运动员详情跳转

其他模块在展示运动员姓名时，建议生成跳转到运动员详情页的链接：

```jinja2
<a href="{{ url_for('players.detail', player_id=athlete_id) }}">
    {{ athlete_name }}

```

### 12.3 injury_status 读取

其他模块如需展示运动员伤病状态，直接读取 `athlete.injury_status` 字段即可，无需查询 `injury_record` 表。状态值与徽章样式的映射可使用 `players.py` 中的 `get_injury_status_badge_class()` 函数。

### 12.4 运动员 ID 校验

在新增训练计划/体能报告/伤病记录时，应校验 athlete_id 是否存在：

```python
from db import execute_query

athlete = execute_query("SELECT id FROM athlete WHERE id = %s", (athlete_id,), fetch_one=True)
if not athlete:
    raise ValidationError("所选运动员不存在。")
```

### 12.5 与成员2触发器模块的协作

- 运动员模块**不主动**修改 injury_status 字段（除非管理员在编辑页手动修改）
- injury_status 由成员 2 部署的触发器自动维护
- 如果触发器未部署（如测试环境），injury_status 可通过编辑页手动管理
- 管理员在详情页可以看到触发器状态的说明卡片

## 附录 A：SQL 注入防护说明

本模块所有数据库操作均使用 PyMySQL 的参数化查询（`%s` 占位符 + 参数元组），**不使用任何字符串拼接来构建 SQL 语句的值部分**。结构部分（表名、列名、ORDER BY）虽然使用 f-string，但来源为用户不可控的硬编码字符串，不存在注入风险。

```python
# ✅ 安全：值来自用户输入，使用占位符
cursor.execute("SELECT * FROM athlete WHERE name LIKE %s", (f"%{name}%",))

# ✅ 安全：ORDER BY 方向来自硬编码
sql = f"SELECT * FROM athlete{where_clause} ORDER BY id DESC"
```
