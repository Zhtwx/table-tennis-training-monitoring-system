## 三、约束设计说明

### 3.1 主键约束

所有核心业务表均采用 `id INT AUTO_INCREMENT PRIMARY KEY` 作为主键。该设计保证每条记录具有稳定、唯一的内部标识，便于外键引用和后端接口传参。

涉及表：

```text
athlete, coach, training_plan, technical_record,
fitness_report, injury_record, user_account, match_record
```

### 3.2 外键约束

本系统使用 InnoDB 引擎维护外键完整性，避免出现训练、体测、伤病、比赛数据找不到对应运动员的情况。

| 子表 | 外键字段 | 父表 | 删除策略 | 设计理由 |
|---|---|---|---|---|
| `training_plan` | `athlete_id` | `athlete(id)` | `CASCADE` | 删除运动员时同步清理其训练计划 |
| `training_plan` | `coach_id` | `coach(id)` | `RESTRICT` | 教练有训练计划时不允许删除 |
| `technical_record` | `athlete_id` | `athlete(id)` | `CASCADE` | 删除运动员时清理技术记录 |
| `technical_record` | `evaluator_id` | `coach(id)` | `SET NULL` | 教练离职后历史评分保留 |
| `fitness_report` | `athlete_id` | `athlete(id)` | `CASCADE` | 删除运动员时清理体测记录 |
| `fitness_report` | `tester_id` | `coach(id)` | `SET NULL` | 教练离职后历史体测保留 |
| `injury_record` | `athlete_id` | `athlete(id)` | `CASCADE` | 删除运动员时清理伤病记录 |
| `match_record` | `athlete_id` | `athlete(id)` | `CASCADE` | 删除运动员时清理比赛记录 |
| `user_account` | `coach_id` | `coach(id)` | `SET NULL` | 账号注销不影响教练档案 |

### 3.3 非空约束

核心业务字段必须设置为 `NOT NULL`，避免出现无法解释的业务数据。

主要包括：

- 运动员：`student_no`, `name`, `gender`, `skill_level`, `injury_status`
- 训练计划：`athlete_id`, `coach_id`, `plan_name`, `start_date`, `end_date`, `intensity`
- 专项技术记录：`athlete_id`, `record_date`
- 体能测试报告：`athlete_id`, `test_date`
- 伤病记录：`athlete_id`, `injury_date`, `injury_location`, `severity`
- 比赛记录：`athlete_id`, `match_date`, `match_name`, `result`
- 用户账号：`username`, `password_hash`, `role`

### 3.4 唯一约束

唯一约束用于保证业务身份不重复。

| 表 | 字段 | 说明 |
|---|---|---|
| `athlete` | `student_no` | 防止重复录入同一运动员 |
| `coach` | `email` | 防止同一邮箱绑定多个教练 |
| `user_account` | `username` | 登录账号必须唯一 |
| `user_account` | `coach_id` | 一个教练最多绑定一个系统账号 |

### 3.5 默认值约束

| 表 | 字段 | 默认值 | 说明 |
|---|---|---|---|
| `athlete` | `injury_status` | `健康` | 新增运动员默认健康 |
| `training_plan` | `status` | `进行中` | 新计划默认进行中 |
| `injury_record` | `recovery_status` | `治疗中` | 新伤病记录默认治疗中 |
| 多数表 | `create_time` | `CURRENT_TIMESTAMP` | 自动记录创建时间 |

## 四、索引设计

索引设计文件位于 `sql/member2_advanced_database.sql`。设计原则是：只围绕高频查询条件、排序字段和统计分组字段加索引，避免盲目增加维护成本。

| 索引名 | 表 | 字段 | 支持场景 |
|---|---|---|---|
| `idx_athlete_name` | `athlete` | `name` | 按姓名查询运动员 |
| `idx_athlete_level_status` | `athlete` | `skill_level`, `injury_status` | 按等级和健康状态筛选 |
| `idx_training_plan_athlete_date` | `training_plan` | `athlete_id`, `start_date`, `end_date` | 查询运动员日期区间训练计划 |
| `idx_training_plan_coach_status` | `training_plan` | `coach_id`, `status` | 教练查看自己负责的计划 |
| `idx_technical_record_athlete_date` | `technical_record` | `athlete_id`, `record_date` | 查询运动员技术训练历史 |
| `idx_technical_record_evaluator_date` | `technical_record` | `evaluator_id`, `record_date` | 查询教练评估记录 |
| `idx_fitness_report_athlete_date` | `fitness_report` | `athlete_id`, `test_date` | 查询运动员体测历史 |
| `idx_fitness_report_tester_date` | `fitness_report` | `tester_id`, `test_date` | 查询教练体测记录 |
| `idx_injury_record_athlete_status` | `injury_record` | `athlete_id`, `recovery_status` | 查询运动员当前伤病 |
| `idx_injury_record_recovery_date` | `injury_record` | `recovery_status`, `expected_recovery_date` | 康复跟踪和预警排序 |
| `idx_match_record_athlete_date` | `match_record` | `athlete_id`, `match_date` | 查询运动员比赛历史 |
| `idx_match_record_result_date` | `match_record` | `result`, `match_date` | 统计胜负结果 |

## 五、视图设计

### 5.1 `v_athlete_comprehensive_profile`

该视图整合运动员基础信息、训练计划数量、技术记录数量、平均技术分、体测记录数量、平均体测分、伤病数量和比赛胜场数。

适用场景：

- 运动员综合档案页
- 教练查看运动员训练概况
- 统计分析大屏
- 答辩演示快速查询

示例：

```sql
SELECT * FROM v_athlete_comprehensive_profile;
```

### 5.2 `v_monthly_training_summary`

该视图按运动员和月份汇总专项技术记录，输出正手、反手、发球、步法、反应和综合分平均值。

适用场景：

- 月度训练报告
- ECharts 折线图/柱状图数据源
- 运动员技术成长趋势分析

示例：

```sql
SELECT * FROM v_monthly_training_summary
WHERE training_month = '2026-06';
```

## 六、存储过程设计

### 6.1 `sp_filter_athletes_by_level`

按运动等级筛选运动员，参数为空时返回全部运动员。

```sql
CALL sp_filter_athletes_by_level('一级运动员');
CALL sp_filter_athletes_by_level('');
```

### 6.2 `sp_get_monthly_training_summary`

按月份查询训练技术汇总，参数格式为 `YYYY-MM`。

```sql
CALL sp_get_monthly_training_summary('2026-06');
CALL sp_get_monthly_training_summary('');
```

### 6.3 `sp_refresh_athlete_injury_status`

根据 `injury_record` 中未恢复的伤病记录，自动刷新 `athlete.injury_status`。

状态规则：

| 条件 | athlete.injury_status |
|---|---|
| 存在 `治疗中` 且 `严重` 的伤病 | `伤病中` |
| 存在 `治疗中` 的伤病 | `观察中` |
| 存在 `康复中` 的伤病 | `康复中` |
| 没有未恢复伤病 | `健康` |

该过程主要由触发器自动调用，也可以手动修复单个运动员状态：

```sql
CALL sp_refresh_athlete_injury_status(1);
```

## 七、触发器设计

触发器用于保证 `athlete.injury_status` 与 `injury_record.recovery_status` 保持一致。

| 触发器 | 触发时机 | 作用 |
|---|---|---|
| `trg_injury_after_insert` | 新增伤病记录后 | 刷新该运动员伤病状态 |
| `trg_injury_after_update` | 修改伤病记录后 | 刷新新旧运动员伤病状态 |
| `trg_injury_after_delete` | 删除伤病记录后 | 刷新该运动员伤病状态 |

测试示例：

```sql
INSERT INTO injury_record (
    athlete_id, injury_date, injury_location, severity, recovery_status
) VALUES (
    1, '2026-07-06', '右膝', '严重', '治疗中'
);

SELECT id, name, injury_status FROM athlete WHERE id = 1;
```

预期结果：`injury_status` 自动变为 `伤病中`。

## 八、权限与安全设计

成员 1 已在 `sql/pingpang_db.sql` 中配置：

| 账号 | 权限 | 用途 |
|---|---|---|
| `admin_app` | `ALL PRIVILEGES` | 管理员、初始化、维护 |
| `coach_app` | `SELECT, INSERT, UPDATE, DELETE` | Flask 业务系统日常访问 |

成员 2 补充：

| 账号 | 权限 | 用途 |
|---|---|---|
| `readonly_app` | `SELECT` | 统计大屏、演示、审计只读访问 |

设计原则：

- Flask 应用不直接使用 `root` 账号。
- 日常业务使用 `coach_app`，只读展示使用 `readonly_app`。
- 管理员账号 `admin_app` 仅用于数据库维护、初始化和结构调整。
- 生产环境中密码应放入 `.env`，不要写入 Python 源码。

## 九、备份与恢复方案

### 9.1 完整备份

建议在每次合并到 `dev`、答辩前、数据库结构调整前进行完整备份。

```powershell
mysqldump -u root -p --databases pingpang_db > backup_pingpang_db_20260706.sql
```

### 9.2 仅备份数据

当表结构稳定，只需要保留业务数据时使用：

```powershell
mysqldump -u root -p --no-create-info pingpang_db > backup_pingpang_db_data_20260706.sql
```

### 9.3 恢复数据库

恢复前建议确认当前库是否可覆盖。

```powershell
mysql -u root -p < backup_pingpang_db_20260706.sql
```

如果只恢复数据，需要先执行成员 1 和成员 2 的建库脚本：

```powershell
mysql -u root -p < sql/pingpang_db.sql
mysql -u root -p pingpang_db < sql/member2_advanced_database.sql
mysql -u root -p pingpang_db < backup_pingpang_db_data_20260706.sql
```

### 9.4 备份命名规范

```text
backup_数据库名_日期.sql
backup_pingpang_db_20260706.sql
backup_pingpang_db_before_demo.sql
```
