## 一、全局设计说明

### 1.1 数据库基本信息

| 项目 | 值 |
|---|---|
| 数据库名 | `pingpang_db` |
| 字符集 | `utf8` |
| 引擎 | `InnoDB` |
| 部署文件 | `sql/pingpang_db.sql` |

### 1.2 实体识别

系统共识别 **7 个核心实体** + **1 个权限实体**：

```
athlete        运动员      — 系统核心实体
coach          教练员      — 训练执行与评估主体
training_plan  训练计划    — athlete 与 coach 的关联桥梁
technical_record 专项技术记录 — 技术评估数据
fitness_report 体能测试报告 — 身体素质测试数据
injury_record  伤病记录    — 运动员伤病档案
match_record   比赛成绩    — 比赛成绩与技战术复盘
user_account   用户账号    — 登录与权限管理
```

### 1.3 E-R 关系

```
athlete 1 ── N training_plan   N ── 1 coach
athlete 1 ── N technical_record N ── 1 coach（评估者）
athlete 1 ── N fitness_report   N ── 1 coach（测试者）
athlete 1 ── N injury_record
athlete 1 ── N match_record
coach   1 ── 1 user_account（可选关联）
```

### 1.4 外键删除策略

| 子表 → 父表 | 策略 | 理由 |
|---|---|---|
| training_plan → athlete | CASCADE | 运动员删除，训练数据随之清理 |
| training_plan → coach | RESTRICT | 教练有训练记录时不允删除，防止遗留孤儿数据 |
| technical_record → athlete | CASCADE | |
| technical_record → coach | SET NULL | 教练离职，评估记录保留（evaluator_id 置空） |
| fitness_report → athlete | CASCADE | |
| fitness_report → coach | SET NULL | |
| injury_record → athlete | CASCADE | |
| match_record → athlete | CASCADE | |
| user_account → coach | SET NULL | 教练账号注销，coach 数据保留 |

### 1.5 约束清单

- **NOT NULL**：所有主键、外键、姓名、日期、必填 ENUM 字段
- **UNIQUE**：athlete.student_no、coach.email、user_account.username、user_account.coach_id
- **DEFAULT**：injury_status 默认'健康'、recovery_status 默认'治疗中'、status 默认'进行中'

## 二、字段命名与数据类型规范

### 2.1 命名规范（全库统一）

| 规则 | 示例 |
|---|---|
| 全部小写 + 下划线分隔 | `athlete_id`、`forehand_score` |
| 主键 | 一律 `id`，INT AUTO_INCREMENT |
| 外键 | `关联表名_id`，如 `athlete_id`、`evaluator_id` |
| 状态字段 | `_status` 后缀，ENUM 类型 |
| 时间字段 | `_time` 后缀，TIMESTAMP 类型 |
| 评分字段 | `_score` 后缀，DECIMAL(5,2) |
| 日期字段 | `_date` 后缀，DATE 类型 |

### 2.2 数据类型标准

| 数据类别 | 类型 | 示例 |
|---|---|---|
| 主键/外键/编号 | `INT` | id, athlete_id |
| 学号/手机 | `VARCHAR(20)` | student_no, contact_phone |
| 姓名/队伍/部位 | `VARCHAR(50~100)` | name, team, injury_location |

## 三、事务一致性代码（ACID 设计）

### 3.1 核心事务场景

**场景**：教练完成一轮评估周期，需同步写入训练计划执行记录 + 当期体能测试结果。两条 INSERT 必须原子执行——要么同时成功（COMMIT），要么同时撤销（ROLLBACK）。

### 3.2 事务代码

```sql
-- 训练计划 + 体能报告同步提交
START TRANSACTION;

INSERT INTO training_plan (
    athlete_id, coach_id, plan_name, start_date, end_date,
    training_content, intensity, hours, status
) VALUES (
    1, 1, '暑期强化集训',
    '2026-07-01', '2026-07-15',
    '每天上午体能训练 2h + 下午技术专项 2h',
    '高', 36.0, '已完成'
);

INSERT INTO fitness_report (
    athlete_id, test_date, tester_id,
    upper_strength, lower_strength, flexibility, endurance, speed, overall_score
) VALUES (
    1, '2026-07-01', 1,
    85.5, 90.0, 78.0, 88.0, 92.0,
    ROUND((85.5+90.0+78.0+88.0+92.0)/5, 2)
);

COMMIT;
```

### 3.3 SAVEPOINT 部分回滚

```sql
-- 主计划已落库，体能数据有问题 → 回滚到保存点，保留训练计划
START TRANSACTION;

INSERT INTO training_plan (...)
VALUES (2, 2, '伤病恢复训练', '2026-07-01', '2026-07-14', ...);

SAVEPOINT after_plan;

INSERT INTO fitness_report (...)
VALUES (2, '2026-07-01', 2, 60.0, 65.0, ...);

-- 体能数据有误 → 回滚体能部分，训练计划保留
ROLLBACK TO SAVEPOINT after_plan;

COMMIT;
```

### 3.4 ACID 四性在本系统的体现

| 特性 | 实现机制 | 系统体现 |
|---|---|---|
| **原子性** | InnoDB undo log | 训练+体能两条 INSERT，同生共死；任意违反外键/约束 → ROLLBACK |
| **一致性** | 主键、外键、NOT NULL、UNIQUE、ENUM 限值 | 事务前→后，所有约束均满足（athlete_id/coach_id 必须引用真实行，评分不超出范围） |
| **隔离性** | InnoDB MVCC + REPEATABLE-READ | 并发写入互不可见中间态；行级锁防脏写 |
| **持久性** | redo log（WAL）+ binlog | COMMIT 后写入 redo log，即使宕机重启数据不丢；binlog 支持增量备份 |

## 四、跨模块接口预留

### 4.1 模块与数据库对象映射

系统前端栏目 → 数据库表的对应关系：

| 前端模块 | 对应表 | 接口说明 |
|---|---|---|
| 运动员档案 | `athlete` | 首屏查询支持 student_no/name/gender/level/play_style/injury_status 联合筛选 + 年龄范围 |
| 新增/编辑运动员 | `athlete` | INSERT / UPDATE，含 student_no 唯一性校验 |
| 训练计划管理 | `training_plan` | athlete_id + coach_id 联表查询，按 start_date 排序 |
| 专项技术录入 | `technical_record` | athlete_id 关联，evaluator_id 记录评估教练 |
| 体能测试评估 | `fitness_report` | athlete_id 关联，tester_id 记录测试教练，支持 Excel 批量导入（openpyxl 解析后逐行 INSERT） |
| 伤病记录管理 | `injury_record` | athlete_id 关联，severity + recovery_status 双字段筛选 |
| 历史伤病 | `injury_record` | 按 athlete_id + injury_date 倒序查询 |
| 康复跟踪预警 | `injury_record` | WHERE recovery_status IN ('治疗中','康复中') ORDER BY expected_recovery_date |
| 比赛成绩报告 | `match_record` | athlete_id 关联，match_date 倒序，按 result 统计胜负率 |
| 统计分析大屏 | 全部表 | ECharts 图表数据源：各表 COUNT/AVG/SUM 聚合 + 按月份/等级分组 |
| 用户权限 | `user_account` | 登录验证：username + password_hash；权限校验：role 字段 |
| 系统配置 | `user_account` | 字典表/参数表可后续由成员 8 单独建表，读 DB 或读 JSON 均可 |

### 4.2 各模块通用连接方式

所有后端模块统一使用 pymysql，上层做 DAO 封装即可：

```python
import pymysql

def get_db():
    return pymysql.connect(
        host='localhost',
        user='admin_app',      # 或 coach_app（生产环境用低权限）
        password='Admin2026#',
        database='pingpang_db',
        charset='utf8'
    )
```

### 4.3 关注事项

- **athlete.injury_status** 字段需要随着 `injury_record` 的增删改同步刷新（成员 2 触发器负责）
- **training_plan** 和 **fitness_report** 的同步写入可在同一个事务中完成（见第三章事务一致性代码）
- **technical_record** 和 **fitness_report** 的评估者/测试者均为 coach，但允许为 NULL（教练删除后记录保留）
